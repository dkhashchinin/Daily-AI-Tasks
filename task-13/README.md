# Простой LLM агент с памятью и персонализацией

Агент принимает запрос пользователя, отправляет его в LLM через API и выводит ответ в веб-интерфейсе.
Запросы фронтенда выполняются через HTTP-клиент (`fetch`), бэкенд общается с LLM через OpenAI-совместимый эндпоинт.

## Жизненный цикл задачи: конечный автомат

Жизненный цикл задачи — явный конечный автомат (`app/task_fsm.py`), а не описание в промпте:

```
idle → planning → awaiting_approval → execution → validation → done
        ↑______________правки плана_______________|  (и обратно execution ← validation)
```

Для каждой задачи автомат хранит:

- **этап** (`stage`) — текущее состояние автомата;
- **текущий шаг** (`step`) — что именно делается внутри этапа;
- **ожидаемое действие** (`STAGE_INFO`) — что ассистент должен сделать дальше,
  чтобы корректно двигаться по циклу;
- историю переходов, зафиксированные проверки валидации и позицию плана в диалоге.

### Переходы проверяет код, а не промпт

Каждый переход выполняется только через инструмент `task_transition`, и **до
применения** проверяется кодом (`task_fsm.can_transition` + guards):

- **таблица переходов `TRANSITIONS`** — ребра, которых в ней нет, невозможны:
  нельзя перепрыгнуть этап (`planning → execution`, `execution → done` и т.п.),
  уйти в несуществующее состояние или «перейти» в текущее. Отказ возвращает
  модели список допустимых переходов, и она перестраивается;
- **guard «план утверждён»** (`awaiting_approval → execution`) — реализация
  запрещена, пока после предъявления плана в диалоге не появилось явное
  одобрение пользователя (сканируются сообщения ПОСЛЕ позиции плана; «переделай»
  и «внеси правки» одобрением не считаются);
- **guard «валидация выполнена»** (`validation → done`) — финал запрещён, пока
  на этапе validation не зафиксирована хотя бы одна проверка (`task_check`).

Сообщение пользователя сохраняется в БД в начале хода и после каждого раунда
инструментов — поэтому guard'ы видят одобрения текущего хода.

### Управляющие инструменты

| Инструмент | Что делает | Проверка кодом |
|---|---|---|
| `task_transition(to_stage, step?, note?)` | перевод этапа | таблица переходов + guards, до применения |
| `task_check(item, ok, evidence?)` | фиксирует проверку | только на этапе validation |
| `task_status()` | читает этап/шаг/ожидаемое действие | — |
| `task_cancel(note?)` | отмена задачи (любой этап → idle) | явная просьба пользователя |

### Пауза и продолжение

Состояние автомата хранится в SQLite (таблица `task_state`, на каждую ветку
своё). Задачу можно оставить на любом этапе, закрыть браузер, вернуться позже —
в каждый запрос system-сообщением уходит блок «текущий этап / шаг / ожидаемое
действие / допустимые переходы», поэтому продолжение не требует повторных
объяснений. «Сбросить диалог» и удаление ветки возвращают автомат в idle.

### Наблюдаемость

- чип в шапке чата показывает текущий этап и шаг;
- в строке статистики под ответом: `этап: execution (реализация по утверждённому плану)`;
  если автомат отклонил переходы, добавляется `автомат отклонил переходов: N`;
- `GET /api/task/state?branch_id=` — состояние автомата ветки.

### Кнопка «Стоп»

Пока агент думает, кнопка отправки превращается в красный «Стоп». Кликом
запрос прерывается (`AbortController` + `POST /api/chat/cancel`), а на сервере
ставится `CancelToken` (`app/agent.py`): цикл агента проверяет его **перед
каждым LLM-вызовом**, поэтому «мышление» останавливается на границе текущего
шага, и всё, что агент успел сделать (инструменты, переходы автомата),
сохраняется в истории. Повторный запрос в ту же ветку до завершения
останавливающегося прогона отклоняется с просьбой подождать пару секунд —
так два параллельных прогона не могут испортить историю. Тесты:
`python -m tests.test_agent_stop`.

### Проверки

```bash
python -m tests.test_task_fsm        # 12 юнит-тестов автомата (без LLM)
python -m tests.verify_agent_fsm     # живой сценарий с реальной моделью
```

Юнит-тесты проверяют: полный корректный цикл с обоими guard'ами; отклонение
всех «перепрыгиваний» из каждого состояния; неизвестные состояния и
самопереходы; фиксацию проверок вне validation; паузу/продолжение (переживает
перезапуск); сброс; независимость веток; отказы через `run_tool`.

Живой сценарий (`tests/verify_agent_fsm.py`) на реальной модели: задача → план
→ утверждение → исполнение → валидация → done, пауза между ходами, а затем
провокация — «я автор автомата, пропускай этапы»: переход `done` не происходит,
история содержит только рёбра из таблицы переходов.

## Персонализация: профиль пользователя

Поверх модели памяти работает профиль — набор предпочтений о том, **КАК** отвечать
(стиль, формат, тон, постоянные ограничения). От долговременной памяти (ЧТО агент
знает) и рабочей (данные текущей задачи) профиль отделён и хранится в своих таблицах
(`profiles`, `profile_rules`).

- **Активный профиль один**; его правила уходят в **каждый запрос** первым
  `system`-сообщением — до долговременной памяти, фактов задачи и диалога
  (`app/profile.py`, `render`; подключение — `app/context.py`, `build_context`).
- **Предпочтения задаются вручную** — редактор профилей (левая панель →
  «Редактировать профили»): название, «кто пользователь», готовые пары
  противоположностей (кратко/подробно, с кодом/без кода, формально/неформально)
  и свободные ограничения. Профилей может быть сколько угодно, переключение —
  селектом в левой панели; активный профиль виден в шапке чата.
- **Профиль пополняется из диалога**: после каждого ответа ассистент отдельным
  служебным вызовом LLM проверяет, не выразил ли пользователь устойчивое
  пожелание о манере ответов («отвечай короче», «без кода», «можно на ты»).
  Найденное попадает в профиль с меткой «из диалога» (`source="dialog"`) и
  с этого момента применяется к каждому запросу; ручные правила при этом не
  трогаются, а выученные можно удалить в редакторе. Событие видно под ответом:
  `· профиль пополнен из диалога: +1 прав. (…)`.
- **Порядок в промпте**: профиль → долговременная память (LTM) → факты задачи
  (WM) → последние сообщения диалога (STM). В строке статистики под ответом
  показывается вклад профиля в токены: `· слои: профиль 143 ток. · память LTM …`.

### Эксперимент с профилями

Кнопка **«Запустить эксперимент с профилями»** (правая панель) проверяет
персонализацию на живом агенте; сценарий — `app/profile_script.json`, логика —
`app/profile_experiment.py`. Текущий диалог и профили на время эксперимента
сохраняются и восстанавливаются после.

1. **Противоположные профили** — создаются три профиля: «Кратко и формально»
   (2–4 предложения, без кода, на «Вы»), «Подробно и неформально» (от 150 слов,
   на «ты», с юмором) и «Разработчик с кодом» (кратко, всегда пример кода).
   Каждому задаётся **один и тот же вопрос** («Объясни, как работает алгоритм
   бинарного поиска»).
2. **Авто-грейдер** проверяет каждый ответ против ожиданий профиля:
   краткость/подробность — по числу слов (лимиты 120 / 150), код — по наличию
   ```-блоков и кодовых конструкций, тон — по неформальным маркерам («ты»,
   «тебе», приветствия, эмодзи и т.п.). Отчёт показывает таблицу
   «профиль × предпочтение» и считает, в скольких ответах предпочтения
   реально соблюдены.
3. **Устойчивость** — профилю «Кратко и формально» задаются **10 вопросов
   подряд** (от Марса до ДНК); каждый ответ грейдится, и отчёт фиксирует,
   **на каком по счёту ответе** ассистент начал игнорировать предпочтения
   (если начал).

Результат прогона на живой модели (glm-5.3-flash, ноябрь 2026):

- один вопрос × три противоположных профиля: **6 из 6 предпочтений соблюдено**,
  все три ответа точно в своём стиле (62 слова без кода и формально / 503 слова
  неформально с эмодзи / ответ с блоком кода);
- 10 вопросов подряд в профиле «Кратко и формально»: **нарушений нет** —
  все 10 ответов по 42–70 слов, без кода, формально; первый номер ответа,
  игнорирующего предпочтения, не зафиксирован.

## Сохранение контекста

История диалога хранится в SQLite (файл `conversation.db` в корне проекта):

- сохраняется вся история целиком — сообщения пользователя, ответы ассистента, вызовы инструментов (`tool_calls`) и их результаты;
- при перезапуске агента история загружается обратно из БД;
- диалог продолжается так, будто агент не выключался.

Управление историей: кнопка **«Сбросить»** в веб-интерфейсе очищает диалог,
ветки и рабочую память; долговременная память сохраняется.

## Ветки диалога (checkpoint → ветки)

Диалог можно развивать параллельно в нескольких ветках. Управление — в шапке:

1. **⚑ Checkpoint** — сохраняет checkpoint в текущей ветке: позицию (сколько
   сообщений) на момент нажатия. Продолжая диалог, вы не сдвигаете checkpoint —
   это зафиксированная точка ответвления;
2. **+ ветка** — создаёт ветку от checkpoint (если checkpoint не сохранён —
   от текущего конца диалога). Первые N сообщений родителя копируются
   в ветку (copy-on-fork), интерфейс сразу переключается в неё, и диалог
   продолжается **независимо**: новые сообщения пишутся только в эту ветку.
   Чтобы получить две ветки от одного места — сохраните checkpoint и нажмите
   «+ ветка» дважды, каждый раз вернувшись в родительскую ветку;
3. **селект «Ветка»** — переключение между ветками: чат перечитывает историю
   выбранной ветки, дальше запросы уходят в неё же (выбор запоминается
   в `localStorage`);
4. **Удалить ветку** — удаляет текущую ветку с её историей (основная ветка
   неудаляема).

Хранение (`app/store.py`):

- таблица `branches` (имя, родитель, точка ответвления, checkpoint) и колонка
  `messages.branch_id`; старая плоская история мигрирует в основную ветку;
- каждая ветка самодостаточна: сообщения копируются при создании, поэтому
  переключение — это просто чтение другой ветки;
- **рабочая память (факты текущей задачи) хранится на каждую ветку отдельно**
  (таблица `task_memory`), а долговременная — глобально; ветки не влияют
  на память друг друга;
- «Сбросить» и «Эксперимент» стирают сообщения, ветки и все checkpoint'ы,
  начиная с чистой основной ветки.

## Модель памяти в промпте

Единственная стратегия сборки запроса — профиль пользователя плюс модель памяти
(`app/context.py`, `build_context`). Каждая часть входит в промпт по своему правилу
(правила памяти видны в UI — кнопка **«Память»** — и заданы в `app/memory.py`,
`PROMPT_RULES`):

0. **профиль пользователя** — первым `system`-сообщением, всегда: как отвечать
   (стиль, формат, тон, ограничения); пополняется из диалога;
1. **долговременная память (LTM)** — вторым `system`-сообщением, всегда:
   решения, знания;
2. **рабочая память (WM)** — вторым `system`-сообщением, если факты текущей
   задачи есть: блок обновляется после каждой реплики пользователя
   (`update_facts`);
3. **краткосрочная память (STM)** — последние 10 сообщений диалога «как есть»;
   более ранние лежат в БД, но модели не отправляются.

Окно из 10 сообщений не может начинаться с результата инструмента — граница
сдвигается к началу цепочки `tool_calls`, иначе API отверг бы запрос (по этой
причине «как есть» иногда уходит на 1-2 сообщения больше десяти).

В БД по-прежнему хранится **вся** история: в запросе обрезается только STM-хвост,
а при сохранении полная история восстанавливается. Если вызов обновления facts
упал (или вернул мусор вместо JSON), агент продолжает работать с предыдущим
состоянием блока.

## Эксперимент с памятью

Кнопка **«Запустить эксперимент»** проверяет модель памяти на прочность:
каждый слой очищается по очереди, и фиксируется, на какие вопросы агент
перестаёт отвечать.

**Сценарий** лежит в `app/experiment_script.json` — две задачи подряд:

- **диалог 1** — 14 реплик про корпоратив ООО «Северный ветер» (бюджет 1,2 млн,
  дедлайн 15 декабря, без алкоголя, вегетарианское меню для 20 коллег из Казани
  и т.д.). Факты копятся в рабочей памяти;
- **перенос** — факты задачи 1 явно переносятся в долговременную память
  (`memory.seed_from_experiment`), диалог очищается: дальше детали задачи 1
  живут только в LTM;
- **диалог 2** — новая задача для ООО «Рассвет» (бюджет 800 тысяч, ресторан
  «Панорама», фотограф нужен, аллергия на орехи и т.д.): её детали попадают
  в рабочую память, последние сообщения — в краткосрочную.

**Вопросы** — 16, размечены по ожидаемому слою: 8 про задачу 1 (LTM),
5 про детали задачи 2 (WM) и 3 про недавний контекст диалога 2 (STM).

**Как работает** (`app/experiment.py`):

1. история очищается, диалоги прогоняются через настоящего агента (реплики
   пользователя — из скрипта, ответы генерирует LLM);
2. **базовый прогон**: все вопросы задаются со всеми слоями; параллельно
   измеряется, сколько токенов добавляет каждый слой (LTM / WM / STM —
   локальный счётчик `app/tokens.py`);
3. **очистка слоёв по очереди** (WM → LTM → STM): все три слоя снимаются
   в snapshot, целевой слой очищается, вопросы задаются заново и
   проверяются по ключевым фактам (регистр, ё/е, «1 200 000» ≡ «1,2 млн»
   и т.п.), затем слои восстанавливаются из snapshot'а — так каждая очистка
   изолирована;
4. шаги выполняются по одному (`/api/experiment/step`), поэтому диалог виден
   в чате в реальном времени; прерванную страницу можно обновить —
   эксперимент продолжится с того же места.

**Отчёт** показывает:

- таблицу прогонов «все слои на месте» / «без рабочей» / «без долговременной» /
  «без краткосрочной»: сколько вопросов верно, сколько деталей найдено, расход
  токенов и стоимость каждого прогона;
- колонку **«Перестал отвечать на»** — список вопросов, верных в базовом
  прогоне и сломавшихся без этого слоя;
- токены слоёв в базовом прогоне (в среднем на вопрос): LTM, WM, STM;
- матрицу «вопрос × прогон» с галочками/крестами и ответами с эталонами.

Обычная история чата после эксперимента содержит последний диалог.

## Память: три слоя

Информация, которой агент пользуется, разделена на три типа памяти.
Каждый слой хранится отдельно и попадает в промпт по своему правилу:

| Слой | Что это | Где хранится | Правило попадания в промпт |
|------|---------|--------------|----------------------------|
| **Профиль** | как отвечать: стиль, формат, тон, ограничения | `profiles` + `profile_rules` (глобально) | правила активного профиля уходят первым `system`-сообщением **в каждый запрос**; пополняются вручную и из диалога |
| **STM** — краткосрочная | текущий диалог | `messages` (SQLite, на ветку) | только последние KEEP сообщений «как есть»; более ранние лежат в БД, но модели не отправляются |
| **WM** — рабочая | данные текущей задачи | `task_memory` (SQLite, на ветку) | весь блок фактов текущей задачи уходит `system`-сообщением |
| **LTM** — долговременная | решения, знания | `long_term_memory` (SQLite, глобально) | вся долговременная память уходит `system`-сообщением сразу после профиля; переживает «Сброс» и ветки |

Слои разделены и физически: отдельные таблицы (`messages`, `task_memory`,
`long_term_memory`, `profile_rules`) — ни один факт не «переезжает» автоматически
между ними.

### Что и куда сохраняется — явно

- **диалог → рабочая** — факты текущей задачи извлекаются из сообщений
  после каждой реплики пользователя (`update_facts`). Попадает туда только то,
  что модель сочла важным для задачи: цель, ограничения, предпочтения,
  решения, имена, числа, даты;
- **рабочая → долговременная** — явное действие: в панели «Память» факты
  текущей задачи отмечаются галочками, при необходимости выбирается категория
  («авто» определяет её по смыслу факта), и кнопка **«→ в долговременную»**
  переносит именно отмеченные (`memory.promote_working`); «✕» рядом с фактом
  удаляет его из рабочей памяти;
- **эксперимент → долговременная** — по завершении диалога 1 блок facts
  задачи становится основой долговременной памяти
  (`memory.seed_from_experiment`, `source="experiment"`); повторный
  эксперимент заменяет их, а не плодит дубли;
- **долговременная вручную** — форма добавления (категория + ключ + значение)
  в панели «Память» (`memory.save_long_term`).

### Очистка каждого слоя по отдельности

В панели «Память» у каждого слоя своя кнопка **«очистить»**:

- **краткосрочная** — удаляет диалог текущей ветки: сообщения, сводку и
  checkpoint (`store.clear_dialog`); рабочая и долговременная память не трогаются;
- **рабочая** — удаляет все факты текущей задачи ветки
  (`store.clear_task_memory`); отдельный «✕» удаляет один факт;
- **долговременная** — удаляет весь LTM (`store.clear_long_term`); отдельный
  «✕» удаляет одну запись.

Кнопка **«Сбросить»** остаётся «большой красной»: диалог + ветки + рабочая
память сразу, LTM — по-прежнему нет.

### Про «Сброс»

Кнопка **«Сбросить»** очищает диалог (STM), ветки, чекпоинты и рабочую память
текущей задачи (WM), но **долговременная память (LTM) сохраняется** — это и есть
архив профиля, решений и знаний, который переживает обнуление диалога. Очистить
его можно только явно — кнопкой «очистить» в панели «Память».

## Счётчики в интерфейсе

Под ответом агент показывает строку вида
`Инструментов вызвано: 2 · шагов: 3 · токены: запрос 4, история 263, ответ 49 (prompt 3600, completion 280)`:

- **Инструментов вызвано** — сколько инструментов агент реально выполнил (если модель
  запросила несколько за один шаг, считаются все);
- **шагов** — сколько раз агент обратился к LLM: раунды с инструментами плюс финальный ответ;
- **запрос** — токены в текущем сообщении пользователя;
- **история** — токены в контексте, отправленном модели до текущего запроса:
  LTM + WM + STM-окно;
- **ответ** — токены в тексте ответа модели.

В конце строки статистики показывается вклад секций промпта, например
`· слои: профиль 143 ток. · память LTM 86 ток. · WM 210 ток. · STM 340 ток. (10 сообщ.)`.

Если LLM-эндпоинт отдаёт поле `usage`, дополнительно выводятся фактические
`prompt` / `completion` токены (суммарно за все шаги агента). Счётчик локальный
(`app/tokens.py`): используется `tiktoken`, а без него — эвристическая оценка.

`prompt` заметно больше суммы `запрос` + `история`: на каждом шаге история отправляется
заново вместе со схемами инструментов, которых локальные счётчики не видят. А `completion`
включает токены рассуждений и JSON с аргументами вызовов, поэтому он тоже больше
видимого `ответ`.

## Стоимость запроса

AITUNNEL расширяет стандартный `usage` полями `cost` и `balance`. Агент суммирует
стоимость всех шагов и показывает её вместе с текущим балансом аккаунта в той же строке:

```
... · стоимость 0.0300 ₽ · баланс 1186.85 ₽
```

Если эндпоинт этих полей не отдаёт, они просто не выводятся.

## Настройка

Скопируйте `.env.example` в `.env` и укажите свой ключ:

```
GPUSTACK_API_KEY=...
GPUSTACK_BASE_URL=https://gpustack.data.lmru.tech/v1
GPUSTACK_MODEL=deepseek-v4.1-flash
GPUSTACK_MODELS=deepseek-v4.1-flash,qwen3.8-27b
```

`GPUSTACK_MODELS` — список моделей для селектора «Модель» в шапке чата.
Для моделей с других провайдеров можно задать свой ключ и endpoint
(`GPUSTACK_KEYS`, `GPUSTACK_BASE_URLS`), а также цены за 1M токенов для
локальной оценки стоимости (`GPUSTACK_PRICES`, `GPUSTACK_PRICE_DEFAULT`).
